# 时延与体验实测

本轮状态（2026-10-21）：按职责重构后的性能未重新测量；以下时延保留原验收版本和采样口径，不作为本轮性能结论。

2026-10-21，Windows x64 本机便携 Python 3.13.16，Agent Server 端口2024、3个后台worker，远端GaussDB与Qwen、本机Redis。以下为小规模开发实测，不能外推生产负载。

## 只读 HTTP

脚本 backend/scripts/measure-http.py：每路由预热一次，顺序采样10次，复用HTTP连接，并发1；P95为最近秩法。原始数据在 backend/tests/reports/http-latency-before.json 与 http-latency.json。测量期间无新增模型/OCR调用，最后一轮有本地回归测试负载。

| 路由 | 当前P50 | 当前P95 |
| --- | ---: | ---: |
| /app/ | 6.60ms | 249.08ms |
| /api/health | 261.67ms | 490.17ms |
| /api/tasks | 209.83ms | 231.28ms |
| 单任务详情（含官方state） | 600.32ms | 857.96ms |

最初任务列表P50约1938ms/P95约2693ms。实际瓶颈是每次从数据库取回完整大产物；改为数据库JSON摘要投影，详情按需读取，前端统计使用record_count/issue_count。对比不是严格隔离实验，报告保留两组原始采样。连接池和阻塞I/O移入线程也已实际接入。

这里没有测量任务POST受理、状态事件到浏览器、暂停生效或三任务并行的完整P95；计划中的≤1秒仍是这些项目的待验目标。前端业务快照每5秒轮询，Agent流另由官方SDK订阅，不能把HTTP延迟直接当成用户看到业务结果的延迟。

## 指定 OCR 实测

OBS启用后，原题PNG的签名下载为200且字节SHA-256与原件一致，OCR请求耗时12.329秒。两份PDF各经自动上传、签名下载哈希校验及指定OCR，下载加OCR分别31.744秒与45.816秒；含上传及本地处理总耗时分别32.734秒和46.893秒。两份PDF并发2执行，PNG的结构化映射使用已保存真实响应回放，没有再次在线调用。报告为 `backend/tests/reports/obs-ocr-real.json` 和 `obs-originals-ocr.json`。

以上是3次原题OCR请求的单次观测，响应为结构化 `data.list`，不代表逐字OCR全文或费用金标准确率。没有将这些有限样本汇总为P50/P95。签名在实际派发前生成，有效期3600秒；传输与OCR分别校验，SDK内部HTTP不独立计为LangChain工具派发。

原题EML任务 `edfd9e4f-a0a7-4aa5-9349-07eb29169cc1` 在3附件自动上传/OCR后，共使用14次模型请求、12次工具派发、163.155秒活跃时间，停在币种与收费双方的人工补充中断。三个附件的结构化chargeList为空，正文保留1条金额50且币种为null的候选；未批准或正式导出。该时间是到人工等待的活跃时长，不是完成财务结果的端到端时间，详见 `backend/tests/reports/obs-agent-task.json`。

## 长材料与后续测量

PDF传输默认20页切片，文档并发3，模型分块采用拥有范围与相邻上下文；人工修订复用原解析。当前长PDF、TIFF多帧和跨页Word只有合成合同/完整性测试。原题短PDF/图片的真实OCR已接通；仍未取得长材料费用准确率、内存峰值或并发吞吐数据。

首个有效结果、排队、OCR/模型等待、人工等待和最终完成应分别报告。真实OCR条件落实后，按短/长/混合附件与缓存命中分组测量，再决定切片、委派、上下文和并发调整；当前不声称长材料性能达标。

## 本轮长材料优化建议：先测边界，再调容量

2026-10-21 对 `document-intake`、`document-extraction`、工具绑定与 harness 的代码核对如下；本节没有新增在线请求或长材料压测，建议项不能当作已实现的加速结果。

| 优先级 | 已实现的基础 | 需要继续落实的优化 |
| --- | --- | --- |
| 1：避免重复工作 | PDF 默认20页生成真实切片；语义层使用官方 splitter，默认6000字符、前后各最多800字符只读上下文；工具每次返回默认8块、最多12块 | 20页仅是默认值。按实际OCR超时/密度试验5、10、20页组；分页读取复用固定分块产物，避免每次读取重新分块。当前 `max_chunks=2000` 在全部构造后截断，尚未形成内存上限，需改为有界生成/读取并保留遗漏范围。 |
| 2：缩短首结果等待 | 官方Agent流已连接，材料解析在线程中运行；完成后保存来源 | 当前 `intake_documents` 等本次 `gather` 全部结束才保存结果。后续按已完成材料/页组持久化可回读产物，让首个有证据的草稿先出现，未处理范围继续显示；保留同一任务与revision约束。 |
| 3：控制模型容量 | 有 `max_tokens=10000` 输出上限、共享模型24次/工具64次/活跃1200秒预算 | 6000字符不是6000 token，输出上限也不是输入容量门禁。按实际Qwen tokenizer或经真实usage校准的保守估算扣除提示、工具schema、历史、邻接上下文及输出预留，再决定本批费用行数；截断只缩小受影响范围。 |
| 4：只重做有疑点的范围 | 按chunk替换已有提取、无进展拒绝、每范围最多两轮修复已经存在；金额/证据/覆盖各自校验 | 简单材料直接抽取；只对缺证据、跨页未闭合、冲突或低支持度字段重读原文并局部复核。新置信度是规则支持度，尚未有自动按低分范围路由的验收，不能把高分当作跳过覆盖的依据。 |
| 5：约束并发与复用 | 单次intake信号量默认3；父子/摘要/重试共用任务调用预算；成功的整件intake结果可缓存24小时 | 当前信号量不等于跨run/worker的全局模型/OCR限流。先测服务配额，再共享模型限速实例；跨进程QPS/TPM与OCR并发需要服务级协调。增加按页组/语义块的版本化缓存，使一个坏页或一次字段修订不迫使整篇重跑。 |

跨页续表应保留唯一费用行的拥有范围：第一页开始的行由其拥有块输出，下一页只提供补全文本，证据同时指向两处。重复表头、承前转后、小计/总计单独标识，不能靠重叠文本直接追加费用。Word沿OOXML内容顺序、表格/行/单元格身份处理；没有固定渲染版本时不按虚构物理页切块。真实OCR只返回页组时保留 `original_pages`，不伪造精确页。覆盖闭合继续作为正式输出门禁，但不能证明OCR没有漏字、模型没有错误排除费用。

后续基准应固定独立人工答案和同一模型/配置版本，按长短、格式、费用密度、跨页类型、冷/热缓存以及并发1/3分组，记录每组样本数和失败/人工介入比例。每次优化先比较漏提/重复费用、金额与币种、证据定位和总额支持，再比较以下时间与资源指标：

- 首反馈：任务受理到浏览器出现任务标识、材料清单或真实进度；不以首条模型token代替。
- 首个有效结果：到第一条有可回读来源的草稿费用/明确校验问题；部分结果带未完成范围。
- 完成时间：受理到当前revision可复核结果，以及最终审批完成分别计时；排队、OCR等待、模型等待、人工等待分别保留。
- 分组P50/P95、峰值内存、模型输入/输出token、调用数、缓存命中、重试与失败率；不得将两次真实模型任务或三次OCR观测汇成负载P95。

官方依据已通过LangChain MCP复核：splitter索引及 `TextSplitter` 的 `length_function`/tokenizer入口、模型的 `rate_limiter`、`InMemoryRateLimiter`、`ModelCallLimitMiddleware` 和原生流式updates。`InMemoryRateLimiter`只限制同进程请求频率，不计算LLM token且不跨进程；因此它不能单独证明TPM或多worker全局限流已完成。安装组合仍为LangChain 1.4.6、langchain-text-splitters 1.1.3、Deep Agents 0.7.29；上述新增组合实施前仍需最小兼容验证。
