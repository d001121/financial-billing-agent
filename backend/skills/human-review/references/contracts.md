# Human revision and approval boundary

2026-10-22 clarification: a supplied entity that still fails the existing posting Hook needs a targeted role/relationship answer. Saved `completed_with_gaps` is an extraction artifact state, not permission to end that unresolved conversation. Optional absent fields remain null without blanket approval; an explicit defer is respected. Use existing party edits and native interrupt/resume, never infer AR/AP from the confidence score.

2026-10-21 policy update: normal bills do not require per-bill human approval. `review_outcome` combines fresh confidence, hard validation and the current export projection; automatic verification writes `auto_review` with complete action/version/argument binding. Human `approval` and `review_confirmation` remain separate facts. A current automatic binding is accepted by `validate_approval`, while every formal export still reruns all financial gates. Only observed low-confidence fields generate a native confidence review. Missing information by itself does not. `completed_with_gaps` means saved editable extraction, not authorization to execute incomplete records. Revision CAS remains mandatory; entity-only edits do not erase partial candidates.

For incremental extraction, merge_extraction preserves unresolved model issues on untouched chunks, deduplicates totals by source/document/currency/role and lets the host recompute generated coverage/evidence issues after merging. Always validate the combined result under the same repository mutation boundary, rather than validating one batch against all source ranges and retaining that temporary missing-coverage error.

Because the host merges raw Pydantic candidates before full-result validation, missing/null charge IDs receive document-extraction's `charge-` hash convention before dictionary indexing. Unique stable source-line/evidence identities reuse an existing ID across batches and row-order changes; the host must not depend on a batch-local numeric position as a permanent source identity. Multiple unassigned rows are retained separately, and matching a confirmed source identity retains the human record ID and its locked fields. Missing evidence or ambiguous identity still requires the applicable business checks.

Host integration: `prepare_recalculation({task,review})` unpacks reviewed records using this Skill's explicit field contract, preserves human_confirmed/selected_match_id and the original source store, and produces charges for billing-reconciliation. `merge_extraction({task,result,replace})` merges model batches under the host's repository mutation lock. It reapplies confirmed field values and preserves deleted/split membership from `task.history[].history` tombstones, including when a model changes charge_id but retains a stable source-line/evidence identity. The host must retain revision history; source identities are not inferred from amounts. Ambiguous line identity is not resolved by fuzzy financial matching.

The recalculation result also replaces the active `extraction` view with the reviewed charges and revision, retains the previous view in `extraction_history`, and invalidates cached evidence/coverage validation. Generated schema/evidence/coverage issues are recomputed from current fields and unchanged source material; a stale issue must not veto a corrected field. Explicit edits remove only matching charge/field semantic issues, while unresolved other fields remain. Split/delete actions update coverage charge membership. The returned candidate view is not marked validated: the host must rerun the native-bound domain hooks.

Standalone CLI: `python scripts/skill.py --input input.json --output output.json` invokes the same `apply_revision` function. Omitted paths or `-` use stdin/stdout. Input and output are UTF-8 JSON with numeric decimal amounts. A valid revision exits 0; rejected revisions or invalid input exit 1 with a structured `issues` result. Output files are resolved from the caller's directory, and resources do not depend on that directory.

- https://docs.langchain.com/oss/python/deepagents/skills — native Skill loading and tool binding remain host responsibilities.

The native middleware already supplies pause/review/resume and parameter-schema checks. It does not define billing revisions, field dependency invalidation, split/deletion audit history or approval binding to financial rule versions. Only those domain contracts are implemented here. No graph runner, queue, custom saver or interrupt engine is added.

`apply_revision` is pure, returns copied records, history, previous_revision, new revision and invalidated names; persistence and atomic expected-revision comparison are host responsibilities. Failed operations return original records. Allowed field paths are explicit. Numeric booleans/non-finite values fail before applying; full business validations run after edits. An invalid batch is atomic in this pure function. Native per_call HITL responses are a separate boundary and must be sent/checkpointed according to the official API, not this batch helper.

`human_confirmed` maps canonical field paths to value and revision. The host must include these in subsequent model input and merge policy; the model may not silently overwrite them. Reconciliation does not automatically mean financial posting approval. `approval_binding` hashes complete action arguments and version metadata deterministically using simplejson's Decimal encoding. `validate_approval` compares the current hash to explicitly approved bindings. An edit changes the hash and requires fresh validation/review. The host persists the exact binding at the controlled dispatch boundary, checks policy and verifies external receipts after retries.
