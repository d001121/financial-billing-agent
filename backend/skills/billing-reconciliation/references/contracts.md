# Contract and official capability check

Grouping uses document_id when provided, so separate logical invoices in one physical PDF cannot contaminate each other's totals; source_id is the fallback scope. Explicit discount line roles normalize amount to -abs(amount), retaining raw_amount. Declared tax/discount totals adjust the aggregate only when that role is not already represented as a fee row; carry-forward, brought-forward and subtotals never add charges. The validator's derived totals use scope_id rather than manufacturing a source occurrence ID from a logical document ID.

Executable records require every evidence link to carry verified=true from current source read-back. Supplied evidence/coverage/extraction errors and incomplete source ranges mark affected proposals PENDING_REVIEW inside reconciliation itself. Both proposal and validation use the same selected_match_id resolver; a valid explicit selection clears matching ambiguity, while a stale/out-of-set selection fails.

Checked using LangChain Docs and API MCP on 2026-10-21. The host owns the installed package lock. Native `create_agent(response_format=ToolStrategy(...))` provides model output validation; built-in middleware supplies tool/model retries, call limits, human review and extension points. None implements the shipping exercise's charge mappings, four-tier bill matching, decimal totals, three-state financial edits or creditor/debtor accounting direction. Only these domain functions are supplied here; there is no custom agent runner or hook engine.

`charges` are flat objects, or exported nested records. Minimum executable proposal: charge_item, amount, ISO4217 currency, explicit accounting_entity, creditor/debtor relationship and evidence. Document fields may remain null when absent; missing values are never invented. `evidence` contains `{source_id,anchor,quote}`; validity is checked against immutable sources by evidence-linking.

Canonical alias mappings: Handling Fee/H/D Fee/H/C (any phrase containing the `H/C` abbreviation, e.g. `Carrier Free H/C`) → Handling Charge; Doc Fee → Documentation Fee; THC → Terminal Handling Charge; Trucking Fee → Trucking Charge; Customs Fee → Customs Clearance Fee; Storage Fee → Storage Charge. A run may supply an explicit `charge_mapping` override; the host pins its rule version. PP/prepaid → PP and CC/collect → CC, preserving raw values.

Version 1.3.2 normalizes the amount scope before comparing totals. A charge without `document_id` and a total with `document_id` are grouped under the same document when that source has exactly one document; the same applies in reverse. This prevents a false `TOTAL_MISMATCH` when the fee line and the printed total describe the same single-document bill but only one row carries the document id. `validate_amounts` accepts an optional `documents` list for this mapping; `reconcile_charges` passes the current documents.

Version 1.3.1 completes printed-title normalization for space-separated headings (`DEBIT NOTE` → `Debit Note`, `GENERAL NOTICE` → `General Notice`, `PRE-ALERT EMAIL` → `Pre-Alert`, etc.), and fills a missing creditor/debtor pair from an explicit `A pay B` source line. The payer becomes debtor, the payee becomes creditor; existing and human-confirmed values are never overwritten. A line that does not contain both roles is ignored.

Version 1.3.0 fixes direction from one stated side. If the caller's entity is the known creditor, the charge is AR even when the payer is not yet known; if it is the known debtor, the charge is AP even when the payee is not known. The unknown counterparty stays null and is not invented. A record with neither side, or with the same party on both sides, still yields `POSTING_UNRESOLVED`; an entity that is neither side still yields the existing unresolved reason. This prevents an explicitly answered "是收款方/是付款方" reply from producing the same AR/AP question again, without deciding direction from document type, PP/CC or amount sign.

Version 1.2.0 adds three deterministic settlements before matching, so an unsupported value never reaches AR/AP or matching. A currency kept only by a symbol quote (`$`, `¥`, `€`, `£`, `₩`, `₹`) with no ISO 4217 code in any `field=currency` quote becomes null and adds `CURRENCY_SYMBOL_AMBIGUOUS`. A `creditor`/`debtor` value that does not appear in its own `field=creditor`/`field=debtor` quotes becomes null and adds `PARTY_UNSUPPORTED`; the missing relationship then yields the existing `POSTING_UNRESOLVED`. Both issues keep the record in `PENDING_REVIEW`; values are never guessed from geography, language, `$`, or the caller's entity. `payment_term` is limited to PP/CC and is kept only when the charge's own evidence prints PP/prepaid or CC/collect; `C`, `COD`, `PAY IMMEDIATELY` and other originals become null with `raw_payment_term` preserved and an audit reason (they do not by themselves force review, because the field is optional). `document_type` maps aliases to the printed heading: `email_pre_alert`/`pre_alert` → `Pre-Alert`, `arrival_notice`/`general_notice`/`pai-cma-notice` → `General Notice`, `pai-zim-notice`/`debit_invoice` → `Debit Invoice`, `debit_note` → `Debit Note`, `credit_note` → `Credit Note`; unknown values remain verbatim.

Version 1.0.1 preserves the actual incoming `charge_item` as `raw_charge_item` when a native structured candidate explicitly contains `raw_charge_item: null` or an empty raw name. A supplied nonempty raw name remains unchanged. This corrects provenance during the existing normalization; it adds no aliases and does not alter matching or conflict gates.

Version 1.1.0 exposes the existing normalization as facts in `validate_amounts`: its result includes `revision` from the input and `normalized_charges`, one entry per input row with `{charge_id,input_amount,amount,currency,line_role}`. `input_amount` is taken from the current original row through `flatten`, respecting nested exported fields; `amount`, `currency` and the role come from the same `normalized` result already used by the amount checks. A missing role is reported as the existing effective `charge` role. Input-supplied claims named `normalized_charges` are ignored. No second discount algorithm is added: for a current source candidate of positive 50 with `line_role=discount`, the existing rule produces -50 and this fact reports that precise relationship, not any other negative value.

A consumer must require a passed current-revision amount check, one fact for the current `charge_id`, current candidate equal to `input_amount` and current output equal to `amount`. An invalid/failed amount result may retain diagnostic normalization facts, but they cannot authorize accepting a value. Normalization facts neither prove the original text nor approve the record; source verification and other hard gates still apply. Proposed records also preserve `raw_currency`, `raw_quantity` and `raw_unit_price` along with existing `raw_amount`; signs, separators and source notation are not overwritten.

This small output-contract addition reuses the current-session Docs MCP structured-output/Pydantic validation and API MCP `langchain.agents.structured_output.ToolStrategy` check (LangChain 1.4.6, Deep Agents 0.7.29). Native schema/execution facilities do not define this project's discount role or amount relationship. The only custom change publishes the existing financial function's result for consumers; no middleware, runner, parser, arithmetic implementation or financial semantics changed. Package verification covers discount 50 to -50, current revision and flattened input binding, preservation of raw fields, refusal to use input-forged facts and failed amount diagnostics.

Matching order: reference_no+charge_item; bill_of_lading+charge_item+currency; booking_no+charge_item+currency; container_no+issuer+recipient+document_date+amount. Only unique matches authorize choosing an old bill. A caller may explicitly select `selected_match_id` from the current valid candidate set. Similar rows never silently collapse. Identical claims across different sources are marked for review until identity is established.

An update directive is `{target_id,changes:{amount:120}}` or `{reference_no,charge_item,changes:{...}}`. Key omission inherits the previous value; explicit null clears it and may then fail required-field validation. Only supported fields may change. NO_CHANGE follows a unique match with no supplied differences. Unsupported/ambiguous instructions remain reviewable. Inputs and outputs are copied; existing bills are not mutated.

Decimal values are retained internally. Serialize financial JSON through billing-export's simplejson path; do not round-trip through binary float. Amount arithmetic checks quantity×unit_price with a configured tolerance between 0 and 0.05 (default 0.01). Totals are grouped by source/document identity and currency; carry-forward, brought-forward and subtotal rows are not expense lines. A Credit Note's sign or name cannot independently reverse direction; creditor/debtor must reflect the original business relationship or the record stays pending.

Outputs: `{valid,issues,records,revision,rule_version}`. Each issue includes code, field, severity, repairable and optional charge_id. Records include exact export groups plus internal provenance, match candidates and issues. No external side effects occur. Function tests validate this contract independently of any live model.

## Automatic historical retrieval, 1.4.0 (2026-10-23)

`retrieve_history({task,historical_tasks})` accepts persisted projections from the host and returns `{existing_records,history_lookup}`. It uses the existing four matching tiers and returns only relevant candidates. Sources must have the same normalized accounting entity, completed/approved status, passed current-revision validation and CREATE/UPDATE rows. Self, deleted, rejected and unresolved tasks are excluded. NO_CHANGE does not create another baseline. The host performs one complete projected scan (`limit=None`), without documents/OCR content or a latest-100 cutoff.

Candidate IDs are namespaced by source task, revision and charge ID. An accepted UPDATE supersedes its exact parent revision through derived `history_match` and `history_identity`; independent rows and competing branches remain ambiguous. Extraction-supplied lineage is discarded. Multiple new rows reusing one old row produce MATCH_REUSED. Update directive names use the same pinned fee mapping as matching; the host persists that mapping for subsequent validation.

Automatic mode requires a searched receipt bound to entity/revision and candidate digest. Approval and formal export recompute current candidates: changed history yields HISTORY_STALE; query errors yield HISTORY_UNAVAILABLE and never authorize CREATE. Missing entity yields waiting_entity. The workbench defaults to automatic mode; API consumers explicitly supplying existing_records/existing_bills keep provided mode. Old tasks lacking history_mode retain their prior scope. Retrieval adds no model/OCR requests. UPDATE remains an explicit-field proposal with inheritance, never a write to another task or an accounting system.

Official capability check: Docs MCP `/oss/python/langchain/tools.mdx` describes native tools and ToolRuntime/Store for application database access; API Reference MCP `langchain_core.tools.convert.tool` confirms native tool binding. ## Standalone CLI

Run `python scripts/skill.py --input input.json --output output.json`. Omit either path or use `-` for stdin/stdout. The default is `reconcile_charges`; `--operation` also accepts `validate_amounts`, `validate_matching`, `validate_updates` or `validate_posting`. Each option invokes that existing function once and returns its JSON envelope. Input must be a UTF-8 JSON object; an input file may contain a BOM. Decimal values remain JSON numbers. Only `valid=true` exits 0. A business rejection or invalid/unreadable input exits 1 with a JSON issue; output IO failures exit 1 with a stderr diagnostic.

Rechecked Docs MCP `/oss/python/deepagents/skills` and API `SkillsMiddleware`/`FilesystemMiddleware` with deepagents 0.7.29. They supply native discovery, disclosure and execution, while this package defines the financial IO contract. The small `argparse` entry selects existing pure functions and adds no runner, loop, loading layer or financial algorithm. Shell execution still needs the caller or an official sandbox backend.
