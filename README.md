# 航账 Harbor

### 面向航运财务的证据驱动智能体

**将多格式单据转化为有来源、可修订、可审核的账单决策。**

航账接入邮件、PDF、图片与 Office 表格，从当前记账主体出发提取费用，识别新增、更新、重复与冲突，输出财务 JSON。项目以 Python、LangChain、LangGraph、Deep Agents、Vue 和 TypeScript 实现。

## 项目难点与我们的贡献

### 1. 多种格式共同描述一笔费用，信息分散且容易重复

**难点：** 邮件正文、附件、表格和扫描件的结构不同；同一费用可能在多处出现，合计、条款和条件收费又容易被误识别为费用。

**贡献：** 实现 EML 递归解析、PDF/图片指定 OCR 接入及 Office 表格读取，保留邮件与附件、原件与派生件的关系。主控批量对照材料，按业务身份关联费用，并区分明细、总计、重复描述和条件条款。

### 2. OCR 返回不完整，模型提取必须有可核对的依据

**难点：** 编号、数量、单价和金额容易混列，币种可能只在表头出现，单个货币符号无法唯一确定币种。

**贡献：** 将原始 OCR 响应、候选字段和来源引用分层保存；模型使用 ref_id，宿主回读原文核验。金额用 Decimal 计算，按单据及币种核对合计；保留原值与歧义，缺失字段为 null。工作台可直接打开原件定位。

### 3. 材料多、上下文杂，反复传全文增加调用成本

**难点：** 邮件签名、运输条款、OCR结构和历史工具输出挤占上下文，重复识别与机械委派还会增加等待。

**贡献：** 短材料批读，长材料按清单检索和窗口扩读；原文外置并保持可回读，引用代替重复抄写。成功 OCR 响应按内容及契约缓存，命中后重建本任务的来源身份。简单任务直接保存核验，复杂疑点才委派专家。

### 4. 新材料有差异，不代表用户授权更新旧账单

**难点：** 重复材料、同名费用和多候选账单难以区分；修改金额时也容易连带丢失币种、单号或付款方式。

**贡献：** 自动检索同主体的合格历史记录，按四级匹配规则判断费用身份。明确更新指令才 UPDATE，只修改授权字段，其余继承；重复内容输出 NO_CHANGE，多候选或冲突进入复核。AR/AP依据当前主体和债权债务关系判断。

### 5. 智能体需要自主处理问题，也要避免重复空转

**难点：** 重复读材料、修复覆盖正确证据、错误参数反复提交和主子 Agent 各自消耗预算，会让任务难以收敛。

**贡献：** 基于原生 middleware 组合共享计量、派发身份、无进展识别和证据保护。参数错误返回具体反馈，误读定向补证，缺事实转为明确待办；保存已有提案与成功回执，人工补充后接续局部修订。预算保护与业务核验分别管理。

### 6. 人工纠错后，系统必须保持字段、消息和审批一致

**难点：** 用户可能在聊天中只删除一项费用或修改一个字段；旧待办、旧版本与异步消息容易干扰当前操作。

**贡献：** 常驻聊天与表单共用版本化修订，当前用户意图优先，未完成待办独立提醒。修改生成新 revision、重算相关结果并使旧审批失效；正式导出复查当前版本。消息按官方检查点顺序与 message.id 衔接实时投影。

### 7. 纠错经验需要沉淀，又不能变成补造财务事实的依据

**难点：** 经验表单难填写，人工规则容易过度泛化；历史经验也可能污染当前单据判断。

**贡献：** 从纠错账单生成 AI 经验草稿，自动绑定来源、主体与版本，人工确认后入库；同主体任务按需 BM25 检索，并提供总开关和单条停用。参考经验与可执行财务规则分别管理，规则通过候选、审核发布与回滚流程维护。

### 8. 领域逻辑要可扩展，执行机制要保持清晰

**难点：** 将解析、财务、模型与存储混在一起难以维护，过度拆分 Agent 又增加同步成本。

**贡献：** 以八个业务 Skill 承载接入、提取、证据、匹配、评分、人工修订、导出和反馈；十一类 Hook 统一约束财务结果。复用 LangChain 主控、Deep Agents 专家、Agent Server 与官方 Vue SDK，职责按 agents、middleware、skills、hooks、harness、infrastructure 分开。

## 运行入口

配置 backend/.env 中的服务后，双击根目录 start.cmd，访问 http://127.0.0.1:2024/app/ 。Windows 本地运行使用 backend/bishi1/ 便携解释器；源码克隆的环境准备见 [后端说明](backend/README.md)，前端构建见 [前端说明](frontend/README.md)。
